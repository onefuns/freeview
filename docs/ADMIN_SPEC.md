> 이 문서는 통합 관리자, 공통 백엔드/API 및 쇼핑몰 관리 기능의 현재 기준이다. 고객이 사용하는 Telegram Mini App 화면은 `STOREFRONT_SPEC.md`를 함께 적용한다. 이전 설계와 충돌하면 본 문서의 최신 버전이 우선하며, `미정` 항목은 구현 확정이 아니다.

### v4 기준선

- 조직은 대리점→판매점→영업점이다.
- 오랜 운영 경험과 예외 처리 편의성을 위해 기존 관리자 UI/UX, 메뉴, 수동 업무 방식을 최대한 유지한다.
- 신규 화면으로 재설계하지 않고 기존 검색 패널, 목록 테이블, 체크박스 일괄처리, 작은 행 버튼, 모달 입력 패턴을 그대로 사용한다.
- 판매점·영업점의 신규 주문은 기존처럼 `주문 요청일 + 주문 내용 자유입력` 방식으로 등록한다.
- 판매점과 영업점의 업무 메뉴·기능은 동일하며 판매점에만 영업점 개설·관리와 영업점 공급가 설정을 추가한다.
- 판매점 직접 신규 주문은 저장 즉시 대리점 목록으로 전달한다. 영업점 신규 주문은 접수중으로 판매점에 먼저 표시하고 판매점 승인 후 대리점으로 전달한다.
- 주문의 업무상태는 기존 `접수중·배송준비중·탁송중·배송완료·주문취소·주문보류·예약`을 사용한다. 조직 승인 여부를 별도의 사용자 노출 상태 단계로 만들지 않는다.
- 대리점은 주문 승인 후 재고를 등록하고 판매점 또는 `판매점+영업점`에 수동 할당한다.
- 대리점 판매관리에서 장비·고객·배송·충전 내역을 저장하면 판매현황과 충전내역 및 예약현황에 반영한다.
- 정산은 금액 입금 시스템이 아니라 주문 건을 선택해 정산 여부를 표시하는 업무다. 대리점→판매점과 판매점→영업점 정산을 별도 관계로 관리한다.
- 쇼핑몰 상품은 기존 상품·모델·요금제·재고 코드와 매칭하지 않는다.
- 판매점·영업점은 자기 쇼핑몰의 분류, 상품명, 이미지, 설명, 판매가, 노출상태와 노출순서를 직접 관리한다.
- 일반 쇼핑몰 상품·주문은 노출·가격·결제용이며 운영 상품·신규주문·재고·장비와 연결하지 않는다.
- 판매점·영업점은 기존 방식으로 작성한 신규주문을 자기 직접 고객계정에 수동 매칭한다.
- 고객 매칭 신규주문에 대리점이 실제 재고를 할당하면 고객 장비를 자동 생성하고 배송·개통완료 후 나의 장비에 노출한다.
- 고객이 나의 장비에서 기존 요금제와 개월 수를 선택해 결제하면 고객주문관리에 기록하고 충전요청을 자동 생성한다.

## 1. 프로젝트 목표

기존 라우터 판매 관리자의 익숙한 UI/UX와 수동 운영 기능을 재구축하면서 다음 기능을 통합한다.

1. 대리점→판매점→영업점 3단계 유통 조직
2. 장비, SIM/eSIM, 요금제, 패키지와 고유 재고 관리
3. 기존 관리자와 동일한 수동 신규 주문·재고·판매·충전이력·정산 처리
4. 결제, 발주, 개통, 충전, 배송, 취소, 환불, 정산의 연결
5. 판매점·영업점별 선택형 Telegram Bot 및 쇼핑몰
6. 판매자별 가격·콘텐츠·결제수단·브랜딩
7. 고객·관리자 알림, 상담, 감사로그

신규 시스템은 기존 시스템을 수정하거나 병행 운영하지 않는다. 기존 시스템은 UI/UX, 업무 순서, 필드와 데이터 이관을 위한 참고 기준이다.

## 2. 시스템 경계와 기준 아키텍처

### POL-ARCH-001 통합 관리자 중심 구조

통합 관리자와 공통 백엔드가 시스템 본체다. Telegram Mini App은 선택적으로 활성화하는 판매채널 모듈이다.

```text
통합 관리자
   │
공통 백엔드/API
   ├─ 조직·권한
   ├─ 상품·가격·패키지
   ├─ 개별재고·예약·할당
   ├─ 고객·주문·결제·환불
   ├─ 발주·승인·개통·배송
   ├─ 충전·구독·정산
   └─ 상담·알림·감사
       │
       ├─ 기존 관리자 수동 주문·충전
       └─ Telegram Mini App 고객주문 보관함
```

### POL-ARCH-002 모듈형 모놀리스 우선

초기 개발은 하나의 백엔드 안에서 도메인 모듈을 분리하는 모듈형 모놀리스를 우선한다. 결제감시, Telegram 알림, 장기 배치처럼 독립 확장이 필요한 업무는 이후 워커 또는 서비스로 분리할 수 있다.

### POL-ARCH-003 멀티테넌시

- 모든 업무 데이터는 `tenant_id`와 `organization_id`로 범위를 제한한다.
- 미니앱 코드를 판매자별로 복사·설치하지 않는다.
- 판매점·영업점은 각자 BotFather Bot을 생성할 수 있다.
- 관리자 계정과 Bot을 직접 연결하지 않고 `user → organization_membership → organization → storefront → telegram_bot` 순서로 연결한다.
- 쇼핑몰은 조직별 선택 기능이며 미사용 조직은 `mini_app_enabled=false`로 기존 수동 관리자만 사용한다.
- Bot Token 등록 후 통합 시스템이 검증, Webhook, 메뉴 버튼, 쇼핑몰 연결을 관리한다.
- Bot URL 또는 `startapp` 값만으로 조직을 신뢰하지 않고 Telegram `initData`를 해당 Bot Token으로 서버 검증한다.
- 초기 운영은 쇼핑몰당 활성 Bot 1개를 기본으로 하되 데이터 모델은 1:N Bot 교체 이력을 지원한다.

### POL-LEGACY-003 충전·개통 메뉴 범위

- `/bd.html?m=chargingOrder2`인 현재 `충전 주문 요청` 화면과 기능은 개발한다.
- 대리점·판매점·영업점에 현재 `충전 주문 요청` 메뉴를 제공한다.
- `/bd.html?m=chargingOrder`인 `충전 주문 요청(old)` 화면과 기능은 제외한다.
- `/bd.html?m=rfo`인 `개통 요청`은 대리점 관리자 필수 메뉴로 개발한다.
- 개통 요청은 신규개통·요금제 변경·정지·정지 해제·해지 접수와 처리상태·완료일·메모를 관리한다.
- 제외되는 구형 충전 화면의 등록·수정·일괄처리 API는 개발하지 않는다.

충전 결과와 기간 관리는 `판매 관리`, `판매 현황`, `충전내역 및 예약현황`에도 계속 표시한다. 구형 충전 데이터가 필요한 경우 읽기 전용 조회 또는 데이터 이관 대상으로만 제공한다.

### POL-LEGACY-004 구현 기준선

- 관리자 화면·필드·권한 기준은 본 문서에 통합한다. 과거 세부 기준은 `archive/LEGACY_ADMIN_BASELINE_SPEC.md`에서 근거자료로만 확인한다.
- 판매점은 기존 판매점 화면을 유지하고 하위 `영업점 관리`, `영업점 공급가 설정`만 추가한다.
- 영업점은 기존 판매점과 같은 업무 화면을 사용하되 자기 조직 데이터만 조회한다.
- 쇼핑몰 고객 화면과 콘텐츠 기능은 레거시 수동 업무와 분리하며 [STOREFRONT_SPEC.md](./STOREFRONT_SPEC.md)를 기준으로 구현한다.

## 5. 상품·패키지·가격

### POL-PROD-001 운영 상품과 쇼핑몰 상품의 분리

- 대리점은 기존 관리자 업무에 사용하는 모델·요금제·재고 코드와 공급가를 관리한다.
- 판매점·영업점의 쇼핑몰 상품은 운영 상품코드와 외래키로 연결하지 않는다.
- 판매점·영업점은 자기 쇼핑몰 상품의 분류, 상품명, 이미지, 설명, 고객 판매가, 노출상태와 노출순서를 자유롭게 관리한다.
- 동일한 실물이나 요금제를 판매하더라도 쇼핑몰 상품 구성과 운영 주문 입력은 별개다.
- 일반 쇼핑몰 상품 주문은 운영 신규주문이나 고객 장비의 생성 근거로 사용하지 않는다.

### POL-PROD-002 패키지와 연장

- 쇼핑몰에 표시되는 최초 구매상품은 판매자가 자유 구성한 노출·결제용 상품이며 실제 장비·요금제 코드와 연결하지 않는다.
- 실제 장비·SIM/eSIM·요금제는 기존 신규주문과 대리점 재고할당에서 확정한다.
- 사용기간 연장은 고객 마이페이지에서 기존 장비의 eSIM 구독만 결제한다.
- 연장 시 장비 실재고를 새로 차감하지 않는다.
- 요금제 변경 없이 같은 요금제를 연장하는 것을 현재 기준으로 하되 최종 정책은 클라이언트 확인이 필요하다.

### POL-PRICE-001 계층별 가격

- 대리점은 판매점 공급가를 상품별로 설정한다.
- 판매점은 영업점 공급가를 상품별로 설정한다.
- 판매점과 영업점은 고객 판매가격을 자유롭게 설정한다.
- 상위 조직은 자신이 받아야 할 공급·정산금액을 기준으로 관리하며 하위 판매자의 고객 판매가격은 기본적으로 조회하지 않는다.
- 주문 생성 시 원본가격, 공급가, 고객 판매가를 스냅샷으로 보존한다.
- 쿠폰·프로모션 기능은 현재 범위에서 제외한다.

## 6. 재고·예약·할당

### POL-STOCK-001 실재고

대리점이 개별 재고를 직접 또는 엑셀로 등록한다. 재고는 유형에 따라 CTN, USIM Serial, 장비 Serial, EID, ICCID, QR/활성화 코드, S/N, SSID, 장비 비밀번호 등을 가진다. 실제 필수 eSIM 식별자는 클라이언트·공급사 확인 후 확정한다.

### POL-STOCK-002 수동 등록·할당

- 신규 주문이 승인되었다고 재고를 자동 예약하거나 자동 차감하지 않는다.
- 대리점이 실물 장비와 SIM/eSIM을 준비한 뒤 기존 재고 등록 화면에서 CTN, USIM Serial, Model, S/N-SSID-PASS를 등록한다.
- 판매점 직접 판매는 `판매점 + 영업점 선택안함`, 영업점 판매는 `판매점 + 영업점`으로 귀속한다.
- 판매점·영업점이 신규주문에 자기 직접 고객계정을 매칭한 경우 대리점 재고할당 시 해당 `customer_id`의 고객 장비·회선·구독을 자동 생성한다.
- 대리점에는 고객 로그인 아이디, Telegram ID·username과 고객계정 관리기능을 제공하지 않는다.
- 대리점 판매관리에서 고객·배송·요금제·충전상태를 저장한 시점부터 판매현황과 충전내역에 노출한다.
- 동일 식별자의 중복 등록과 중복 할당은 DB 제약으로 차단한다.

## 7. 주문 접수와 공통 처리

### POL-ORDER-001 접수경로

관리자 수동 주문은 운영 주문으로 관리한다. 미니앱 일반상품 주문은 별도 고객 주문 보관함에만 기록하고 운영 신규주문과 연결하지 않는다. 운영 신규주문은 기존 방식으로 별도 작성한 뒤 판매점·영업점이 자기 고객계정을 수동 매칭한다. 나의 장비 연장 주문만 결제완료 시 충전요청을 자동 생성한다.

권장 `order_source`:

- `ADMIN_MANUAL`
- `TELEGRAM_MINIAPP`
- `PHONE`
- `SMS`
- `KAKAO_TELEGRAM`
- `EXTERNAL_STORE`

### FLOW-ORDER-001 관리자 수동 주문

```text
판매점 직접: 자유 텍스트 신규 주문 저장
→ 판매점 신규 주문 진행에 접수중 표시
→ 대리점 신규 주문 요청에 즉시 표시
→ 대리점이 배송준비중·탁송중·배송완료 등 상태 처리
→ 동일 상태가 판매점에 동기화

영업점: 자유 텍스트 신규 주문 저장
→ 영업점 신규 주문 진행에 접수중 표시
→ 소속 판매점 신규 주문 진행에 승인대기로 표시
→ 판매점 승인 후 대리점 신규 주문 요청에 표시
→ 대리점 상태가 판매점과 영업점에 동기화

공통 후속: 대리점 재고 등록·조직 할당
→ 고객 매칭 신규주문이면 실제 장비를 customer_id에 자동 귀속
→ 판매관리에서 배송·충전내역 저장
→ 판매현황·충전내역 및 예약현황 반영
→ 배송·개통완료 후 고객 미니앱 나의 장비 노출
→ 관계별 건별 정산 표시
```

미니앱을 사용하는 판매자도 예외·오프라인 주문을 위해 수동 주문 기능을 계속 사용한다.

역할별 상세 버튼과 상태는 본 문서의 관리자 화면 기준을 따른다. 사용자 화면은 기존 관리자 주문 목록을 유지하고 조직 단계만 다음처럼 확장한다.

```text
판매점 직접 주문: 판매점 → 대리점
영업점 주문: 영업점 → 판매점 승인 → 대리점
```

### FLOW-ORDER-002 일반 쇼핑몰 주문과 운영 신규주문 분리

```text
고객이 판매자 Bot에서 미니앱 실행
→ 상품·가격·결제수단을 해당 storefront 기준으로 조회
→ 주문 및 결제
→ 고객 주문관리 목록에 기록
→ 일반 쇼핑몰 상품은 운영 신규주문·재고·요금제와 미연결

별도 운영 흐름: 판매점·영업점이 기존 방식으로 텍스트 신규주문 작성
→ 자기 직접 고객계정을 신규주문에 수동 매칭
→ 판매점 직접 주문은 대리점 전달
→ 영업점 주문은 판매점 승인 후 대리점 전달
→ 대리점 실제 재고할당
→ 고객 장비 자동 생성 및 배송·개통완료 후 앱 노출
```

일반 쇼핑몰 결제완료는 운영 주문 접수나 최종 출고 승인이 아니다. 일반상품 결제로 자동 재고예약·자동 발주·자동 충전요청을 수행하지 않는다.

### FLOW-ORDER-003 나의 장비 연장 자동접수

```text
고객이 나의 장비에서 실제 장비 선택
→ 현재 요금제는 변경하지 않고 연장 개월 선택
→ 결제 주문 생성 및 고객 주문관리에 기록
→ 결제완료
→ customer_asset_id·subscription_id·기존 요금제·개월 수로 충전요청 자동 생성
→ 대리점 충전 주문 요청에 접수중 표시
→ 대리점이 실제 충전 수동 처리
→ 충전완료 시 만료일 갱신 및 미니앱 반영
```

결제 주문 한 건당 충전요청 한 건을 DB 제약과 멱등키로 보장한다. 자동 생성 실패 건은 판매점·영업점 고객주문관리에서 확인하되 중복 생성하지 않는다.

고객이 일반 쇼핑몰 주문을 취소하면 고객 주문관리의 주문상태와 결제·환불상태만 변경하며 운영 신규주문·장비에는 영향을 주지 않는다. 나의 장비 연장 주문이 취소되면 생성된 충전요청의 진행단계를 확인해 접수취소·환불·정산 조정을 연결한다.

## 10. 충전·개통·배송

### POL-RECHARGE-001 현재 충전 주문 요청 유지

- 현재 `충전 주문 요청` 메뉴, 반복 요금제 등록 폼, 요청 목록과 상태처리 화면을 개발한다.
- `충전 주문 요청(old)`은 개발하지 않고, 별도 `개통 요청`은 대리점 관리자에 개발한다.
- 충전 결과, 예약, 만료일, 요금제 가격과 메모는 기존과 같은 `판매 관리` 및 `충전내역 및 예약현황`에도 연계해 표시한다.
- 개통일은 `신규 주문 요청` 처리와 `판매 관리` 상세에 기록한다.

### POL-ADMIN-UI-001 기존 목록형 운영 UI

- 신규 주문 요청에는 체크박스 선택 후 적용하는 `주문상태 일괄 변경`을 항상 표시한다.
- 충전 주문 요청의 CTN은 판매 관리 상세로 이동하는 링크이며 별도 수정·보기 열은 사용하지 않는다.
- 검색·필터는 기존 관리자처럼 제목이 있는 회색 검색 조건 패널, 짧은 입력 높이와 정돈된 열 배치를 공통 사용한다.
- 판매 관리는 `판매 목록 → 선택 회선 상세 → 해당 회선 충전 내역` 구조를 유지한다.
- 목록의 모든 메모는 공통 `메모` 버튼을 눌러 동일한 입력 모달에서 등록·수정한다.
- 자유 게시판은 공통 리치 텍스트 에디터와 다중 파일 첨부를 사용한다.
- 코드 관리는 좌측 마스터 코드와 우측 선택 마스터의 서브 코드 목록을 동시에 보는 2단 구조로 구현한다.

### POL-EXPORT-001 엑셀 분리 컬럼

- 화면에서 `CTN / USIM Serial`, `Model / 통신사`, `고객명 / 연락처`처럼 한 셀에 함께 보이는 값도 엑셀에서는 각각 독립 컬럼으로 내보낸다.
- 판매현황 내보내기에는 CTN, USIM Serial, Model, 통신사, S/N-SSID-PASS, 고객명, 연락처를 분리한다.
- 충전내역 내보내기에는 위 항목과 요금제, 요금제 가격, 충전일, 충전시각, 만료일, 메모를 각각 분리한다.
- 현재 권한과 검색조건의 데이터만 내려받고 다운로드 사용자·시각·조건을 감사로그에 남긴다.

### POL-RESPONSIVE-001 관리자 반응형

- 좌측 네비게이션은 접기·펼치기를 제공하며 접을 때 본문이 가용 폭을 사용한다.
- 일반 모바일에서는 메뉴를 오프캔버스로 숨기고 폼을 1열로 배치하며 표는 가로 스크롤로 원형을 보존한다.
- 모바일 브라우저의 데스크톱 사이트 모드처럼 데스크톱 뷰포트가 제공되면 카드형으로 변환하지 않고 데스크톱 관리자 비율과 목록 구조를 그대로 표시한다.

권장 배송 상태:

```text
배송불필요 / 배송준비 → 발송완료 → 배송중 → 배송완료
                                  └→ 반송 / 분실 / 재배송
```

`유심 선발송`, `미충전발송`, `미개통발송`은 하나의 주문상태가 아니라 배송·충전·개통 상태 조합으로 표현한다.

### POL-RECHARGE-002 구독 연장 후보

- 고객 마이페이지 연장은 쇼핑몰 기능 검토 항목 `STORE-013`, `STORE-017`, `STORE-018`에서 별도로 결정한다.
- 채택 전에는 레거시 관리자 기준선의 충전 이력·예약·만료일 조회만 구현한다.

### POL-SHIP-001 배송

수령인, 연락처, 우편번호, 주소, 배송방식, 택배사, 송장번호, 출고일, 배송완료일을 구조화한다. 부분출고·묶음배송·직접배송 허용 범위는 클라이언트 확인이 필요하다.

## 11. 정산

### POL-SETTLE-001 정산 원칙

- 대리점은 판매점 공급가 기준으로 받을 금액을 관리한다.
- 판매점은 영업점 공급가 기준으로 받을 금액을 관리한다.
- 고객 판매가격과 상위 조직 정산금액은 분리한다.
- 부분정산은 금액 분할이 아니라 목록에서 일부 주문 건만 선택해 정산 표시하는 방식이다.
- 대리점 정산 목록은 대리점→판매점 공급가를, 판매점 정산 목록은 판매점→영업점 공급가를 기준으로 한다.
- 정산 버튼은 실제 송금이나 결제를 실행하지 않고 선택 건의 정산상태와 정산일을 기록한다.
- 취소·환불은 역분개 또는 조정 거래로 반영한다.

정산 공식, 부가세, 배송비·개통비·보증금·반품비, 부분입금 충당 순서는 미정이다.

## 12. 고객·Telegram 계정·상담

### POL-CUST-001 내부 고객키

- 고객은 Telegram 계정과 독립된 내부 `customer_id`를 가진다.
- Telegram 계정은 `customer_identities`로 분리하고 연결·해제 이력을 보존한다.
- 최초 가입은 Telegram 인증 후 로그인 아이디·비밀번호만 생성하고 이름·휴대폰·이메일을 회원 필수정보로 수집하지 않는다.
- 주문의 수령인 이름·연락처·주소는 고객계정이 아니라 주문별 수령정보로 저장한다.
- 동일 Telegram 계정은 자동 로그인하고, 새 Telegram 계정은 로그인 아이디·비밀번호가 일치하면 동일 customer_id에 연결한다.
- 새 Telegram 계정 연결 후 이전 identity는 비활성화하며 비밀번호 원문은 저장·표시하지 않는다.
- URL 파라미터나 Telegram username만으로 고객을 확정하지 않는다.

### POL-CUST-002 고객 소유권

- 고객계정 전체를 조직이 소유하는 것이 아니라 실제 고객 장비마다 판매점 또는 영업점의 판매귀속을 기록한다.
- 판매점이 영업점 고객을 자동으로 자기 고객으로 조회하지 않는다.
- 판매점·영업점 고객검색과 신규주문 매칭은 자기 직접 고객·장비 범위로 제한한다.
- 영업점 종료 시 거래 귀속과 서비스 관리권 이전을 구분한다.

### POL-SUPPORT-001 상담

미니앱 상담은 비동기 1:1 문의 티켓으로 제공하되 UI는 채팅 형태로 구현한다. 티켓 상태, 담당자, 메시지, 첨부, 처리이력, 보관기간을 관리한다.

## 13. 쇼핑몰·Bot·알림

### POL-STORE-001 선택형 쇼핑몰

- `mini_app_enabled=false`: 관리자 수동 기능만 사용
- `mini_app_enabled=true`: 관리자 수동 기능과 독립 쇼핑몰·고객 주문관리를 함께 사용
- 일반 미니앱 상품 주문은 운영 주문·재고·발주·충전에 자동 반영하지 않는다.
- 나의 장비 연장 결제만 실제 장비·구독을 기준으로 충전요청을 자동 생성한다.

### FLOW-STORE-001 개설

```text
판매점/영업점 쇼핑몰 신청
→ BotFather에서 Bot 생성
→ Bot Token 등록
→ 시스템이 getMe로 검증
→ 대리점 승인
→ Webhook·메뉴버튼·Mini App URL 설정
→ 독립 분류·상품·가격·결제수단·브랜딩 설정
→ 테스트
→ 활성화
```

관리자 변경·추가·비밀번호 변경은 조직에 귀속된 쇼핑몰 테넌트에 영향을 주지 않는다. 한 조직에 권한 있는 관리자 여러 명을 둘 수 있으며 쇼핑몰 미사용 조직에는 상품·배너·리뷰·고객주문 메뉴를 활성화하지 않는다.

### POL-STORE-002 배너

- 판매점·영업점은 자기 쇼핑몰 메인의 상단·중단·하단 배너를 관리한다.
- 배너는 이미지, 대체텍스트, 위치, 노출기간, 노출순서, 노출상태, 클릭 연결유형·대상을 가진다.
- 클릭 연결은 없음, 쇼핑몰 상품, 상품 분류, 외부 URL을 지원한다.
- 활성기간과 숨김상태를 모두 통과한 배너만 위치별 순서대로 Mini App에 노출한다.

### POL-STORE-003 별점·한 줄 리뷰

- 결제완료된 일반 쇼핑몰 주문상품의 구매고객만 주문상품당 리뷰 한 건을 작성할 수 있다.
- 리뷰 입력은 별점 1~5와 최대 100자의 한 줄 텍스트다.
- 판매점·영업점 관리자는 자기 쇼핑몰 리뷰를 조회하고 노출·숨김할 수 있지만 별점·원문은 수정할 수 없다.
- 숨김·복구는 사유가 필수이며 관리자·일시·이전값을 감사로그와 리뷰 상태이력에 남긴다.
- 상품 평균별점과 리뷰수는 노출중 리뷰만 집계한다.

Bot Token은 암호화 저장하고 평문 표시·로그 기록을 금지한다. 토큰 교체, 폐기, Webhook 실패와 재등록 이력을 보존한다.

### POL-NOTI-001 알림

공통 알림 이벤트를 판매자별 Bot으로 라우팅한다. 고객과 관리자별 필수·선택 알림을 구분하고 실패 재시도 큐와 발송이력을 둔다.

필수 후보:

- 결제 확인
- 영업점 주문 승인·반려와 대리점 전달
- 환불 진행·완료
- 개통·충전 완료 또는 실패
- 출고·배송
- 구독 만료 사전 안내

## 14. 권한·보안·감사

### SEC-001 서버측 권한

- 메뉴 노출과 별개로 모든 API에서 역할·행위·조직 범위를 검증한다.
- 사용자가 전달한 `organization_id`, `tenant_id`, 가격, 정산액을 그대로 신뢰하지 않는다.
- 대량처리, 삭제, 정산, 환불, 재고 재배정, 엑셀 다운로드는 별도 고위험 권한으로 관리한다.

### SEC-002 개인정보

- 연락처, 주소, CTN, USIM/ICCID, Serial, SSID/PW를 역할별로 마스킹한다.
- 검색, 상세조회, 다운로드, 수정, 삭제, 상태변경을 감사로그에 기록한다.
- 고객 판매가격, 판매자 지갑주소, Bot Token을 조직 범위에 따라 보호한다.

### SEC-003 인증·비밀정보

- 비밀번호는 Argon2id 또는 동급 알고리즘으로 해시한다.
- 관리자 MFA, 로그인 실패 제한, 세션 만료와 재인증을 적용한다.
- Bot Token, 결제 비밀정보는 KMS 또는 애플리케이션 암호화로 저장한다.
- Telegram Mini App `initData`는 해당 Bot Token으로 서버에서 검증하고 `auth_date` 만료를 확인한다.

### SEC-004 감사·삭제

- 핵심 감사로그는 변경 불가 형태로 저장한다.
- 실데이터는 기본적으로 논리 삭제 또는 사용중지한다.
- 결제·정산·재고·고객 연결 데이터는 연관 이력 없이 물리 삭제하지 않는다.
- 보존기간과 개인정보 파기정책은 별도 확정한다.

## 18. 비기능 요구사항

### REQ-NFR-001 정합성

- 고유 재고 중복판매를 허용하지 않는다.
- 결제, 예약, 발주, 환불, 정산은 재시도에도 중복 생성되지 않아야 한다.
- 일괄 처리 결과는 성공·실패 건을 분리해 제공한다.

### REQ-NFR-002 가용성

- 미니앱 또는 Telegram 장애 중에도 관리자 수동업무를 계속할 수 있어야 한다.
- 외부 연동 실패는 업무 데이터 손실 없이 재시도한다.

### REQ-NFR-003 성능

- 목록과 검색은 서버 페이지네이션을 적용한다.
- 대량 엑셀 다운로드는 권한과 기간·건수 제한을 두고 필요 시 비동기로 생성한다.

### REQ-NFR-004 추적성

- 주문, 재고, 결제, 발주, 충전, 배송, 환불, 정산의 전체 타임라인을 한 주문에서 조회할 수 있어야 한다.
- 상태 변경자, 시각, 사유, 이전값과 새 값을 기록한다.

## 19. 테스트·인수 기준

최소 검수 시나리오:

1. 판매점이 수동 주문을 저장하면 접수중으로 표시되고 대리점 목록에 즉시 나타난다.
2. 영업점 수동 주문은 접수중으로 판매점에 나타나며 판매점 승인 후에만 대리점 목록에 나타난다.
3. 판매점·영업점 미니앱 주문이 해당 직접 판매조직의 고객 주문관리에만 기록된다.
4. 일반 쇼핑몰 주문·결제만으로 운영 주문, 개별재고 예약, 발주, 충전 요청이 생성되지 않는다.
5. 주문 반려·취소 시 환불업무가 생성되고 이미 할당된 재고만 귀속 해제된다.
6. 판매자는 쇼핑몰 분류·상품·이미지·설명·판매가·노출순서를 기존 코드 연결 없이 관리할 수 있다.
7. 미니앱 미사용 판매점도 관리자 수동 기능을 모두 사용할 수 있다.
8. 판매점은 영업점이 직접 판매한 고객계정·Telegram 정보와 고객 판매가격을 조회할 수 없다.
9. 대리점→판매점과 판매점→영업점 정산이 각 공급가 기준으로 계산되고 선택 주문 건만 정산 표시된다.
10. 판매점·영업점은 기존 자유입력 신규주문을 자기 직접 고객계정에 수동 매칭할 수 있다.
11. Telegram 계정 재연결 후 기존 customer_id의 고객 주문·장비·구독이 유지된다.
12. 잘못된 Bot Token과 위조된 `initData`가 거부된다.
13. 권한 없는 직접 URL/API 접근이 거부된다.
14. 현재 충전 주문 요청과 대리점 개통 요청은 메뉴·등록·목록·상태처리를 제공하고 충전 주문 요청(old)은 존재하지 않는다.
15. 모든 고위험 변경과 다운로드가 감사로그에 기록된다.
16. 판매점과 영업점의 업무 메뉴와 화면 구성이 동일하고 데이터 범위만 다르다.
17. 판매점만 기존 판매점 관리형 UI에서 영업점을 개설하고 메뉴권한·시작페이지를 설정할 수 있다.
18. 대리점 주문 화면은 선택 상태변경, 선택삭제, 신규 주문 등록, 행별 상태·개통일·처리메모 저장을 제공한다.
19. 대리점이 재고를 판매점 직접 또는 판매점+영업점으로 할당할 수 있다.
20. 대리점 판매관리 저장 후 판매현황과 충전내역 및 예약현황에 동일 조직귀속·고객·요금제 정보가 표시된다.
21. 대리점 주문상태 변경이 판매점과 영업점 목록에 동일하게 반영된다.
22. 대리점에는 고객 로그인 아이디·Telegram 정보·고객 장비관리 메뉴가 노출되지 않는다.
23. 고객 매칭 신규주문에 대리점이 실제 재고를 할당하면 고객 장비가 자동 생성된다.
24. 배송·개통완료된 고객 장비만 미니앱 나의 장비에 노출된다.
25. 고객이 나의 장비에서 현재 요금제의 연장 개월을 선택해 결제하면 고객주문과 충전요청이 각각 한 건 생성된다.
26. 자동 충전요청 완료 시 고객 장비 만료일이 갱신되고 판매점·영업점 고객주문관리와 미니앱에 반영된다.
27. 관리자 계정 교체 후에도 조직에 연결된 쇼핑몰 테넌트·Bot·상품·고객·배너·리뷰가 유지된다.
28. 미니앱 미사용 조직은 기존 수동 관리자 기능을 모두 사용하고 쇼핑몰 메뉴는 활성화되지 않는다.
29. 판매점·영업점은 자기 쇼핑몰의 상단·중단·하단 배너를 기간·순서·연결대상과 함께 관리한다.
30. 결제완료된 고객만 주문상품별 별점 1~5와 최대 100자의 한 줄 리뷰를 한 건 작성할 수 있다.
31. 관리자는 리뷰 별점·원문을 변경할 수 없고 숨김·복구 사유와 변경이력이 기록된다.
32. 숨김 리뷰는 상품 평균별점·리뷰수와 미니앱 리뷰목록에서 제외된다.
33. 상품 등록·수정의 스마트 에디터에서 이미지와 링크를 삽입한 뒤 저장·재진입해도 동일하게 복원되고 미니앱 상품 상세에 안전하게 렌더링된다.

## 20. 개발 단계

### 1단계: 정책·상태·범위 확정

- 확인필요 질문에 대한 클라이언트 답변
- 상태전이, 환불, 공급확정, 정산 공식 확정
- 화면목록과 개발 제외 확정

### 2단계: 공통 기반

- 멀티테넌트 조직·권한
- 고객, 상품, 패키지, 가격, 재고 데이터 모델
- 감사로그와 공통 코드

### 3단계: 통합 관리자·수동 업무

- 수동 주문
- 재고 등록·조직 할당·영업점 주문 승인
- 개통·충전·배송
- 결제·환불·정산

### 4단계: 쇼핑몰 관리 모듈

- 독립 storefront 분류·판매상품·콘텐츠·가격·노출순서
- 조직별 선택형 미니앱 설정과 Bot·도메인 연결
- 상단·중단·하단 배너와 별점·한 줄 리뷰 관리
- 고객계정과 기존 수동 신규주문 매칭
- 고객 장비관리와 재고할당 자동 귀속
- 일반상품 주문과 나의 장비 연장주문 분리
- Bot 등록·검증·승인

### 5단계: Telegram Mini App

- Telegram 인증, 로그인 아이디·비밀번호 계정 재연결
- 독립 쇼핑몰 상품, 고객 주문, 결제, 나의 장비
- 위치별 배너 노출과 상품별 별점·한 줄 리뷰 작성
- 동일 요금제·개월 수 연장 결제와 충전요청 자동 생성
- 알림과 1:1 문의

### 6단계: 전환·시범운영

- 초기 상품·재고 등록
- 판매점 시범운영
- 전체 회귀 테스트
- 백업·롤백 리허설
- 신규 시스템 단독 오픈

## 22. 현재 미확정 사항

상세 질문은 통합 요구사항 관리대장의 `확인필요` 시트를 기준으로 한다. 특히 다음 항목은 구현 확정 전에 답변이 필요하다.

- 공급확정과 미수금 발생 시점
- 단계별 취소·환불 가능조건
- USDT 주문 자동매칭과 환불정책
- 수동결제 확인 전 대리점 재고 할당 허용 여부
- eSIM 필수 식별정보
- 패키지 부분출고 허용 여부
- 부분정산 충당순서와 기타비용
- 연장기간과 만료일 계산
- 오프라인 고객정보와 개인정보 동의
- 영업점 종료 시 고객 관리권
- 배송 주체, 부분출고, 재배송
- Bot 생성·교체·폐기 운영 주체
- 과거 올드 충전 데이터의 조회·이관 필요 여부
